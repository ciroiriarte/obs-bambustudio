## Projects and layout

| Channel | OBS project | Tracks |
|---------|-------------|--------|
| stable | `home:ciriarte:bambustudio:stable` | newest upstream release not marked pre-release |
| beta | `home:ciriarte:bambustudio:beta` | newest upstream release of any kind |

The parent `home:ciriarte:bambustudio` holds no packages. Each OBS package
holds only `_service` and `_constraints`. The service pulls the channel's
recipe from this repo's `main` (obs_scm) and the upstream tarballs (download_files).

```
packages/<channel>/bambustudio/     # channel = stable | beta
  _service                   # OBS: recipe from this repo (obs_scm) + download_files
  _constraints               # disk/memory for the bundled deps + the static link
  bambustudio.spec           # bundled Source list generated by tools/gen_deps.py
  bambustudio.changes
  bambustudio-rpmlintrc
project/
  _meta.xml                  # parent project (no repos)
  <channel>/_meta.xml        # repositories, arches, debuginfo   (osc meta prj -F)
  <channel>/_config          # prjconf                           (osc meta prjconf -F)
  <channel>/bambustudio.meta.xml   # package meta
tools/
  gen_deps.py                # regenerate the bundled Source list from an upstream tree
  vendor_web.py              # build + publish the device_page npm store, set %web_store
  bump.py                    # upstream release tracker per channel (run daily by CI)
.github/workflows/upstream-bump.yml
```

## Dependency policy

Libraries come from the target distribution wherever it ships a version Bambu
Studio builds against: GTK3, WebKitGTK 4.1, GStreamer, OpenSSL, curl, FFmpeg 7,
OpenCV, assimp, GLEW, GLFW, NLopt, cereal, libharu, GMP/MPFR, freetype,
libpng/libjpeg/libtiff, expat, zlib.

Only these are bundled, because the distributions cannot provide a usable version:

| Bundled | Why |
|---------|-----|
| wxWidgets (bambulab fork) | Bambu Lab's patched fork; distributions ship stock 3.2 |
| Boost 1.84 | Boost 1.87+ removed `asio::io_service`, which upstream still uses |
| OCCT 7.6, CGAL 5.4, OpenVDB 8.2 (+Blosc, OpenEXR) | the distro versions changed API; upstream pins and patches these |
| TBB 2021.5 | needed statically by the static Boost/OpenVDB build |
| libnoise (bambulab fork) | not packaged by distributions |
| OpenMeshCraft (bambulab) | not packaged by distributions; required since 2.9.1 |

They are built from upstream's superbuild (`deps/CMakeLists.txt`) as static
archives inside the build directory, linked into `bambu-studio`, and discarded
with the build tree. The RPM ships only the binary and `/usr/share/BambuStudio`:
no `.so`, `.a`, headers or `Provides:` for any bundled library.

The link uses `-Wl,--exclude-libs,ALL`, so bundled symbols are not exported and
cannot interpose on a distribution copy loaded at runtime. `%check` fails the
build if `bambu-studio` links or exports any bundled library.

**Unbundling a library:** when a distribution ships a compatible version, set
its `DEP_BUILD_*=OFF` and/or drop it from `%deps_targets`, add the system
`BuildRequires`, and re-run `tools/gen_deps.py`.

## Adapting upstream to system libraries

Upstream's CMake assumes its own bundled copies; the spec bridges the
differences. Each step checks that it applied and fails the build otherwise, so
an upstream change surfaces as a clear `%prep` error on the next bump.

| Where | Adjustment | Why |
|-------|------------|-----|
| `%prep` | `<hpdf/...>` includes → `<...>` | system libharu installs `hpdf*.h` flat in `/usr/include` |
| `%prep` | `cereal` INTERFACE target → `cereal::cereal` | system cereal exports only the namespaced target; the bare name became `-lcereal` |
| `%prep` | `opencv_world` → `${OpenCV_LIBS}` (core, imgproc, imgcodecs) | distro OpenCV is per-module, not the monolithic world library |
| `%prep` | `glewInit()` → `glewContextInit()` | distro GLEW is GLX-only; `glewInit()` fails on EGL contexts (`GLEW_ERROR_NO_GLX_DISPLAY`) |
| `%prep` | CLI thumbnails: OpenGL 3.3 on the native context API | upstream passes GLFW's library version as the GL version ("3.5" with GLFW 3.5) and forces OSMesa |
| `%prep` | `main()` defaults `SSL_CERT_FILE` to the distro CA bundle | the closed network plugin bundles its own OpenSSL with no valid CA path here; upstream's static builds set the variable, ours link the system OpenSSL (without it: curl error 60, no printers) |
| `%prep` | drop the `OSMesa` link | never called directly (GLFW dlopens it); current Mesa no longer ships libOSMesa |
| `%install` | delete `include/mcut`, `/usr/LICENSE.txt`, `/usr/README.md` | the vendored, statically linked mcut installs its dev files into the prefix |
| configure | `-DCMAKE_SKIP_INSTALL_RPATH=ON` | upstream sets a `$ORIGIN` RUNPATH on Linux (rpmlint badness 10000) |
| BuildRequires | `libquadmath-devel` | Boost.Multiprecision includes `quadmath.h` when GCC enables `__float128` |

## Building offline on OBS

OBS build workers have no network, but upstream's build downloads things.

### Bundled dependencies

1. `tools/gen_deps.py` configures upstream's superbuild (configure only) with
   the spec's `%deps_cmake_flags`, asks ninja for a dry run of `%deps_targets`
   (following ExternalProject dependencies, e.g. OpenVDB → Blosc, OpenEXR), and
   writes one `SourceNNN:` line per needed tarball (`<url>#/dep__<Dir>__<file>`).
2. OBS's `download_files` service fetches those URLs.
3. `%prep` copies each into `deps-dl/<Dir>/<file>`, where ExternalProject looks;
   it verifies upstream's own SHA256 and skips the download.
4. The wxWidgets fork, which upstream clones unpinned from `master`, is replaced
   by a tarball of a pinned commit (`%wx_commit`: the fork's `master` at the
   upstream release date).
5. Some recipes download more themselves (OpenMeshCraft fetches Eigen,
   parallel-hashmap, oneTBB and fmt from a generated script). `gen_deps.py`
   collects those URL + SHA256 pairs as Sources too (`nested__<Dir>__<file>`),
   and `%prep` rewrites each URL to a `file://` path (`%nested_fetches`);
   upstream's hash check still applies.

Guardrail: `gen_deps.py` aborts if a bundled dependency becomes git-cloned,
loses its SHA256, or downloads in a way it does not recognize, so a bump cannot
silently produce a recipe that needs network. Never hand-edit the generated
block between its BEGIN/END markers.

### Device page web frontend

Upstream builds the TypeScript/Vite UI in `src/slic3r/GUI/DeviceWeb/device_page`
by downloading Node.js and pnpm and running `pnpm install` against npm. On OBS:

- **Node.js** is the distribution's (`BuildRequires: nodejs >= 22`).
- **pnpm** is its npm tarball at upstream's `PNPM_VERSION`, run by the distro
  `node` (`%pnpm_version`, Source3).
- **npm packages** come from a pnpm store that `tools/vendor_web.py` builds with
  `pnpm fetch` against upstream's `pnpm-lock.yaml` and publishes as a release
  asset of this repo (`web-store-<id>`, Source4). `<id>` is the first 12 hex
  digits of the lockfile's SHA256, so versions with the same lockfile share one
  asset. It includes native optional packages for linux x64 and arm64.

`%prep` seeds the `node-cache` directory upstream's CMake checks with the distro
`node` and an offline `pnpm` wrapper (`install --offline --frozen-lockfile`), so
the frontend is still built from source without network.

## Maintainer workflow

### Automatic upstream bumps

`.github/workflows/upstream-bump.yml` runs daily and processes both channels.
When a channel's pick is newer than its packaged version it runs
`tools/bump.py --channel <ch>`: regenerate bundled sources, publish the npm
store if the lockfile changed, pin wxWidgets, bump the spec and `.changes`. It
then pushes to `main` and fires the OBS runservice token for that channel.

The job installs the GL development files (the superbuild's configure step
looks for OpenGL) and Node.js 22 (for `vendor_web.py`).

If a new release needs a recipe change (a new bundled dependency, or a `%prep`
step that no longer applies), the run or the OBS build fails and the previous
package stays published. Fix the spec and re-run.

Manual bump: `tools/bump.py --channel stable|beta [--version 02.08.02.61]`,
review, commit, push, then re-run the service. `--dry-run` only reports.

### After changing a recipe

Push to `main`, then re-run the service:

```sh
osc service remoterun home:ciriarte:bambustudio:stable bambustudio   # and/or :beta
```

Or run the *upstream bump* workflow manually with `runservice` ticked.

Recipe fixes usually land in beta first. When stable reaches that version,
carry the fix over to `packages/stable/bambustudio/bambustudio.spec`, keeping
stable's `Version`, `%upstream_ver`, `%wx_commit` and generated Source block.

### Local test build

```sh
osc co home:ciriarte:bambustudio:stable bambustudio && cd home:ciriarte:bambustudio:stable/bambustudio
osc service manualrun
osc build openSUSE_Slowroll x86_64
```

Expect about 25 GB of disk and a few hours.

### One-time OBS setup

```sh
osc meta prj home:ciriarte:bambustudio -F project/_meta.xml     # parent
for ch in stable beta; do
  P=home:ciriarte:bambustudio:$ch
  osc meta prj     $P -F project/$ch/_meta.xml
  osc meta prjconf $P -F project/$ch/_config
  osc meta pkg $P bambustudio -F project/$ch/bambustudio.meta.xml
  osc co $P bambustudio && cp packages/$ch/bambustudio/{_service,_constraints} $P/bambustudio/
  (cd $P/bambustudio && osc addremove && osc commit -m "Source the recipe from GitHub")
done
```

Runservice token for CI (no OBS password is stored in GitHub):

```sh
osc token --create --operation runservice   # no project/package binding: serves both channels
gh secret set OBS_SERVICE_TOKEN -R ciroiriarte/obs-bambustudio
```
